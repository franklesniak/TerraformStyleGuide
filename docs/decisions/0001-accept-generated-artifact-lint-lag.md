# Decision 0001: Accept that regenerated artifacts are linted one cycle late

## Status

Accepted on 2026-08-01 by Frank Lesniak, TerraformStyleGuide repository owner.

This records a deliberate, dated acceptance of a known integrity limitation. It is not a
statement that the limitation does not exist, and it is not a to-do item. If any of the
review triggers in the last section fire, this decision must be reopened.

## 1. The concern, and whether it is real

Issue #20 introduces an explicitly temporary pre-promotion writer in
`.github/workflows/build.yml`. After a push to `main`, the `temporary-writer` job
regenerates the four generated artifacts and commits them with the message
`chore: update generated style guide artifacts [skip ci]`.

`[skip ci]` instructs GitHub not to start any workflow run for that commit. Separately,
`.github/workflows/markdownlint.yml` checks out `${{ github.sha }}` — the commit that
triggered it. Those two facts combine: the commit carrying the regenerated bytes starts no
run, and every run that does start sees the artifacts as the contributor committed them,
never as the generator rewrote them.

The concern was raised by an automated reviewer during the review of pull request #26 and
is real.

## 2. What actually goes wrong, and what does not

Scoping matters here, because the raw statement — "the regenerated bytes are never
linted" — is stronger than the truth.

The outer lint command globs the whole repository:

```text
markdownlint-cli2 "**/*.md" "#node_modules" "#.github/workflows/node_modules"
```

The four generated artifacts are matched by that glob. They are therefore linted on the
next triggering event, not never. The exposure is a lag, not an absence.

| Claim | Accurate? |
| --- | --- |
| The regenerated bytes are never linted | No. They are linted on the next push or pull request. |
| `main` can carry unlinted generated bytes for a period | Yes. The window is however long until the next event. |
| A violation is attributed to the wrong change | Yes. It surfaces against whatever arrives next, not against the merge that produced it. |
| A malformed artifact can reach consumers unnoticed | Yes, for the duration of the window. |
| Any credential or write capability is exposed | No. This is a reporting and integrity gap only. |

The real loss is attribution. A formatting defect introduced by a generator change is
reported against an unrelated later contributor, which wastes their time and obscures the
actual cause.

## 3. Options considered

Options were drawn from several role perspectives so the list is not just an engineer's
list.

- **A. Accept and document only.** Record the residual; change nothing operationally.
- **B. Delete `[skip ci]` from the writer's commit message.** The writer's own commit then
  triggers both workflows, so the regenerated bytes are linted immediately.
- **C. Delete `[skip ci]` and make `verify` fail on artifact drift.** Restores a loop
  guard by refusing to proceed when the generated files differ from the committed ones.
- **D. Delete `[skip ci]` and add an author condition to the writer's `if:`** so the job
  never fires on its own bot-authored commits.
- **E. Run both Markdown lint phases inside the writer before it commits.**
- **F. Trigger the Markdown workflow on `workflow_run` completion of the build workflow.**

### Why B is not the obvious one-token fix it appears to be

`[skip ci]` is quietly doing a second job that is not written down anywhere: it is the only
thing preventing the writer from re-triggering on its own commit.

The `verify` job classifies artifact drift without failing on it. Exit status 1 from
`git diff --quiet` means *drift*, and the step records it and passes:

```powershell
$objDiff = Invoke-GitRaw (@('diff', '--no-ext-diff', '--no-textconv', '--quiet', '--') + $arrArtifacts)
if ($objDiff.ExitCode -ne 0 -and $objDiff.ExitCode -ne 1) { throw "..." }
Write-Host "generated-artifacts diff classification: $($objDiff.ExitCode)"
```

Remove `[skip ci]` and the sequence becomes: the writer pushes a commit, that commit starts
a build, `verify` passes regardless of drift, the writer regenerates and finds drift again,
and pushes again. If generation is byte-deterministic the loop stops after one extra cycle.
If it is ever not, the loop does not stop — on `main`, in a job holding a write-scoped
token.

### How the perspectives differed

| Perspective | Position |
| --- | --- |
| Senior engineer | B is one token and closes the gap, but it silently removes a loop guard nobody documented. D is the smallest change that keeps the guard. |
| New contributor | A and B are legible. C is confusing, because failing a verification job to prevent a loop reads as unrelated to its purpose. |
| DevOps | Any option that removes `[skip ci]` adds a full CI cycle per artifact-changing merge. Acceptable, but not free. |
| Documentation | A is mandatory regardless of the technical choice; an undocumented residual is one nobody re-evaluates. |
| Project management | The writer is deleted by issue #22. Work invested in it is written off on a known date. |
| Security executive | Wants the residual owned, dated, and given review triggers rather than left implicit. |
| Security engineer | C is disqualified on inspection: failing `verify` skips `temporary-writer` entirely, because that job is gated on `needs.verify.result == 'success'`. It would stop promotion, not protect it. |
| Business stakeholder | A cosmetic defect on `main` for one CI cycle does not justify structural risk in a component scheduled for deletion. |

## 4. Evaluation rubric

Weights deliberately place technical correctness above effort. Churn, difficulty, and
scope adherence are weighted at half the value of the correctness and safety criteria, so
a cheap option cannot win on cheapness alone.

| Criterion | Weight | What a 5 means |
| --- | --- | --- |
| Closes the lint lag | 1.0 | Regenerated bytes are linted in the cycle that produces them. |
| Preserves the loop guard | 1.0 | The writer cannot re-trigger on its own commit. |
| Preserves promotion | 1.0 | The writer still runs when it legitimately should. |
| Correct attribution of a failure | 1.0 | A violation is reported against the change that caused it. |
| Avoids introducing a new failure mode | 1.0 | No new way for the pipeline to break or hang. |
| Auditability | 1.0 | The residual and its owner are visible in the record. |
| Amount of churn | 0.5 | Few files touched. |
| Difficulty to implement | 0.5 | Little work, little expertise required. |
| Adherence to issue #20 scope | 0.5 | Does not disturb the authorized implementation paths. |

Maximum attainable weighted score is 31.5.

Option C is disqualified on its merits regardless of score: failing `verify` on drift skips
`temporary-writer`, which is gated on `needs.verify.result == 'success'`. It would prevent
the promotion it is meant to protect. Option E is excluded by the pull request #26
description, which states that no candidate validator is introduced.

## 6. Decision

**Option A is selected: accept the residual and document it here.**

Option D scores highest and would be the correct choice if this writer were permanent. It
is not. Issue #22 deletes the `temporary-writer` job outright, and its global workflow
invariants already forbid the mechanism by name:

> Do not use workflow-level path filters or a skip-commit convention.

Choosing D would add new eligibility logic to a job with a scheduled deletion date, in a
component that cannot be executed or tested in the review environment, to close a
cosmetic-attribution gap for the interval until #22 lands. The compensating controls
recorded as the basis for acceptance are:

1. The regenerated bytes *are* linted, on the next triggering event. The gap is a lag.
2. The generator's output is byte-deterministic and proven so across three host matrices,
   so artifact content changes only when a source guide or the generator changes.
3. Issue #22 forbids skip-commit conventions outright, so the mechanism cannot survive the
   rewrite.
4. Nothing about this residual involves credentials, permissions, or write capability.

## 7. What to do about it, step by step

No repository setting or workflow change is required. One tracking action is required so
the acceptance is discharged rather than forgotten:

1. Confirm that issue #22 retains the global invariant *"Do not use workflow-level path
   filters or a skip-commit convention"*. It is present as of 2026-08-01.
2. When #22 is implemented, verify no commit message produced by the promotion writer
   contains `[skip ci]` or any equivalent.
3. Update this record's Status section to **Superseded by #22** at that point, naming the
   landed commit. Do not delete the record; a dated acceptance remains part of the audit
   trail after the condition that prompted it is gone.

## 8. When this decision must be revisited

Reopen this decision if any of the following becomes true.

- The `temporary-writer` job stops being temporary, or issue #22 is closed without
  replacing it.
- Issue #22's prohibition on skip-commit conventions is relaxed or removed.
- A generated artifact is ever consumed by something that would be harmed by malformed
  Markdown reaching `main` for one CI cycle.
- The `verify` job is changed to fail on artifact drift, which would alter the loop-guard
  analysis in section 3 and make option B viable.
- Artifact generation stops being byte-deterministic, which would make the unbounded-loop
  scenario reachable rather than hypothetical.
- The repository gains contributors other than the owner, since misattributed lint failures
  cost other people time.
