# Decision 0001: Accept that regenerated artifacts are linted one cycle late

## Status

**Superseded on 2026-08-02.** The `temporary-writer` job was deleted from T1A, so nothing
commits regenerated artifacts to `main` and the lag this record accepts cannot occur. The
residual is closed by removal rather than by any of the options scored below.

It is in fact closed more completely than any option here achieved. `verify` now **fails**
when the committed artifacts differ from generator output, so the committed bytes and the
generated bytes cannot diverge at all — and the committed bytes are linted as ordinary
repository files on every event. There is no window, not merely a shorter one. Section 3's
distinction between a lag and an absence no longer applies to anything.

That change was only available because the writer is gone. Section 4 records why: failing
`verify` on drift would have skipped `temporary-writer`, which was gated on
`needs.verify.result == 'success'` — it would have blocked the promotion that resolved the
drift. Option C was disqualified on exactly that ground. With no writer to skip, the
disqualification lapses and the strongest option becomes the obvious one.

Promotion is now owned entirely by issue #22, whose design must satisfy the same concern
from a clean start: if its writer pushes with `GITHUB_TOKEN`, that push begins no workflow
run, so the promoted bytes need a lint path that does not depend on a `push` trigger. That
requirement is recorded in section 8 and remains live for #22.

The record is retained rather than deleted. It is the dated reasoning behind a decision that
was in force, and section 10 documents a correction worth keeping: the trigger behaviour it
originally relied on was wrong.

## 1. The concern, and whether it is real

Issue #20 introduces an explicitly temporary pre-promotion writer in
`.github/workflows/build.yml`. After a push to `main`, the `temporary-writer` job
regenerates the four generated artifacts and commits them with the message
`chore: update generated style guide artifacts [skip ci]`.

Separately, `.github/workflows/markdownlint.yml` checks out `${{ github.sha }}` — the commit
that triggered it. The commit carrying the regenerated bytes starts no workflow run, so
every run that does start sees the artifacts as the contributor committed them, never as
the generator rewrote them.

The concern was raised by an automated reviewer during the review of pull request #26 and
is real.

## 2. Why the commit starts no run — and why the marker is not the reason

The original version of this record attributed the absent run to `[skip ci]`. That was
wrong, and the correction matters because it changes which options are even capable of
fixing the problem.

The writer pushes with `${{ github.token }}`. GitHub's documented behaviour is:

> When you use the repository's `GITHUB_TOKEN` to perform tasks, events triggered by the
> `GITHUB_TOKEN` will not create a new workflow run, with the following exceptions

The exceptions are `workflow_dispatch`, `repository_dispatch`, and `pull_request` with
`opened`, `synchronize`, or `reopened` — none of which this push produces. So the artifact
commit would start no `push` run **even if `[skip ci]` were deleted**.

Two consequences follow:

- `[skip ci]` is redundant. It is not a loop guard, it is not load-bearing, and removing it
  changes no observable behaviour of this workflow.
- Deleting it does not cause the regenerated bytes to be linted. The option that looks like
  a one-token fix is not a fix at all.

## 3. What actually goes wrong, and what does not

The raw statement — "the regenerated bytes are never linted" — is stronger than the truth.
The outer lint command globs the whole repository:

```text
markdownlint-cli2 "**/*.md" "#node_modules" "#.github/workflows/node_modules"
```

The four generated artifacts are matched by that glob, so they are linted on the next event
that is *not* a `GITHUB_TOKEN` push — any human push, or any pull request. The exposure is
a lag, not an absence.

| Claim | Accurate? |
| --- | --- |
| The regenerated bytes are never linted | No. They are linted on the next human push or pull request. |
| `main` can carry unlinted generated bytes for a period | Yes. The window lasts until the next such event. |
| A violation is attributed to the wrong change | Yes. It surfaces against whatever arrives next, not against the merge that produced it. |
| A malformed artifact can reach consumers unnoticed | Yes, for the duration of the window. |
| Removing `[skip ci]` would shorten the window | No. The push carries `GITHUB_TOKEN`, so it starts no run either way. |
| Any credential or write capability is exposed | No. This is a reporting and integrity gap only. |

The real loss is attribution. A formatting defect introduced by a generator change is
reported against an unrelated later contributor, which wastes their time and obscures the
actual cause.

## 4. Options considered

Options were drawn from several role perspectives so the list is not just an engineer's
list.

- **A. Accept and document only.** Record the residual; change nothing operationally.
- **B. Delete `[skip ci]` from the writer's commit message.** Ineffective, per section 2.
- **C. Delete `[skip ci]` and make `verify` fail on artifact drift.**
- **D. Delete `[skip ci]` and add an author condition to the writer's `if:`.**
- **E. Run both Markdown lint phases inside the writer before it commits.** The only option
  that closes the lag without changing how the commit is pushed.
- **F. Trigger the Markdown workflow on `workflow_run` completion of the build workflow.**
  `workflow_run` is not suppressed the way `push` is, so this genuinely reaches the new head.

### How the perspectives differed

| Perspective | Position |
| --- | --- |
| Senior engineer | Once the trigger behaviour is understood, B and D collapse: they change nothing. Only E and F can close the lag. |
| New contributor | A is legible. B is actively misleading — it looks like a fix and is not, which is worse than leaving the marker alone. |
| DevOps | F is the idiomatic answer to "lint a commit CI did not start," but it adds a second workflow-triggering path to reason about. |
| Documentation | A is mandatory regardless of the technical choice; an undocumented residual is one nobody re-evaluates. |
| Project management | The writer is deleted by issue #22. Work invested in it is written off on a known date. |
| Security executive | Wants the residual owned, dated, and given review triggers rather than left implicit. |
| Security engineer | C is disqualified on inspection: failing `verify` skips `temporary-writer` entirely, because that job is gated on `needs.verify.result == 'success'`. It would stop promotion, not protect it. |
| Business stakeholder | A cosmetic defect on `main` until the next contributor push does not justify structural change in a component scheduled for deletion. |

## 5. Evaluation rubric

Weights deliberately place technical correctness above effort. Churn, difficulty, and
scope adherence are weighted at half the value of the correctness criteria, so a cheap
option cannot win on cheapness alone.

The criterion "preserves the loop guard" appeared in the original rubric and has been
removed: section 2 establishes there is no loop to guard against.

| Criterion | Weight | What a 5 means |
| --- | --- | --- |
| Closes the lint lag | 1.0 | Regenerated bytes are linted in the cycle that produces them. |
| Preserves promotion | 1.0 | The writer still runs when it legitimately should. |
| Correct attribution of a failure | 1.0 | A violation is reported against the change that caused it. |
| Avoids introducing a new failure mode | 1.0 | No new way for the pipeline to break, hang, or mislead. |
| Auditability | 1.0 | The residual and its owner are visible in the record. |
| Amount of churn | 0.5 | Few files touched. |
| Difficulty to implement | 0.5 | Little work, little expertise required. |
| Adherence to issue #20 scope | 0.5 | Does not disturb the authorized implementation paths. |

Weights sum to 6.5, so the maximum attainable weighted score is **32.5**.

Option C is disqualified on its merits regardless of score: failing `verify` on drift skips
`temporary-writer`, which is gated on `needs.verify.result == 'success'`. Option E is
excluded by the pull request #26 description, which states that no candidate validator is
introduced.

## 7. Decision

**Option A is selected: accept the residual and document it here.**

The two options that could genuinely close the lag are E and F. Both are structural changes
to a job that issue #22 deletes outright, and neither can be executed or tested in the
review environment. The compensating controls recorded as the basis for acceptance are:

1. The regenerated bytes *are* linted, on the next human push or pull request. The gap is a
   lag, not an absence.
2. The generator's output is byte-deterministic and proven so across three host matrices,
   so artifact content changes only when a source guide or the generator changes.
3. Issue #22 forbids skip-commit conventions outright, so the marker cannot survive the
   rewrite. That requirement is already present and needs no amendment.
4. Nothing about this residual involves credentials, permissions, or write capability.

`[skip ci]` is retained rather than deleted. It is redundant, but removing it would be a
change to a write-enabled job that alters no behaviour, and it would misrepresent the
residual as handled.

## 8. What to do about it, step by step

No repository setting or workflow change is required. One tracking action is required so
the acceptance is discharged rather than forgotten:

1. Confirm that issue #22 retains the global invariant *"Do not use workflow-level path
   filters or a skip-commit convention"*. It is present as of 2026-08-01.
2. When #22 is implemented, verify no commit message produced by the promotion writer
   contains `[skip ci]` or any equivalent, and confirm the successor's linting reaches the
   promoted bytes — which, if it still pushes with `GITHUB_TOKEN`, requires something other
   than a `push` trigger.
3. Update this record's Status section to **Superseded by #22** at that point, naming the
   landed commit. Do not delete the record; a dated acceptance remains part of the audit
   trail after the condition that prompted it is gone.

## 9. When this decision must be revisited

Reopen this decision if any of the following becomes true.

- **The writer's push credential changes from `GITHUB_TOKEN` to a personal access token or
  a GitHub App installation token.** This is the most important trigger. Such pushes *do*
  start workflow runs, which simultaneously closes the lag and makes `[skip ci]` load-bearing
  as a genuine loop guard. Every conclusion in sections 2 through 7 depends on the current
  credential.
- The `temporary-writer` job stops being temporary, or issue #22 is closed without
  replacing it.
- Issue #22's prohibition on skip-commit conventions is relaxed or removed.
- A generated artifact is ever consumed by something that would be harmed by malformed
  Markdown reaching `main` until the next contributor push.
- Artifact generation stops being byte-deterministic, which would widen how often the
  window opens.
- The repository gains contributors other than the owner, which raises the cost of
  misattributed lint failures.

## 10. Revision history

- **2026-08-01, initial.** Attributed the absent workflow run to `[skip ci]` and treated the
  marker as the only loop guard, on the assumption that removing it would cause the writer
  to re-trigger on its own commit. Scored six options against a rubric whose stated maximum
  (31.5) did not match its own weights, and reported percentages against that wrong maximum.
- **2026-08-01, revised.** Automated review established that pushes made with `GITHUB_TOKEN`
  start no workflow run, so the marker is redundant and no loop is possible. The loop-guard
  criterion was removed from the rubric, all options were rescored against the corrected
  behaviour, and the arithmetic was recomputed from the published weights. The decision to
  accept is unchanged; option A now wins because the cheap options accomplish nothing
  rather than because the cheap options were dangerous.
